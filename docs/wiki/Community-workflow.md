# Community workflow

Use the narrowest GitHub feature that matches the request.

## Discussions: Q&A

Use **Q&A** when the main goal is to understand, troubleshoot, or apply a skill and there is not yet evidence of a repository defect.

Good questions include relevant versions, the target outcome, what has already been tried, and sanitized evidence.

## Discussions: Ideas

Use **Ideas** for:

- new skill proposals;
- substantial capability expansion;
- changes to skill boundaries or routing;
- contributor-experience improvements;
- design questions where multiple approaches are viable.

Discussion should establish the problem, constraints, and acceptance criteria before a large implementation begins.

## Issues

Use an **Issue** for actionable repository work with a defined problem and expected outcome.

- Use **Bug report** for reproducible incorrect or unsafe behavior.
- Use **Feature request** after a proposal is sufficiently concrete to track implementation.
- Do not file public security vulnerabilities as issues.

## Pull requests

Pull requests should be focused, reviewable, and linked to the relevant issue or discussion when one exists. Include validation evidence and call out compatibility, security, operational risk, and rollback implications.

## Security reports

Follow `SECURITY.md`. Keep exploit details private until maintainers have validated the issue and users have a reasonable mitigation or update path.

## Moderation

Repository participation is governed by `CODE_OF_CONDUCT.md`. Maintainers may redirect posts to the correct channel, close duplicates, lock resolved or disruptive threads, and remove content that exposes sensitive information.
